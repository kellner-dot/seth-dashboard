# KaviTV Playback Fix — 2026-10-04

## Problem
All three KaviTV channels (Horror, Experimental, Independent) failed in Emby.
~18 transcode attempts in 2 hours, all dying the same way.

## Root cause
Emby's HLS pipeline requires the **client** to supply a `PlaySessionId` — Emby
echoes it into every segment URL. Nobody was sending one:

- v0.1.x relay 302-redirected to Emby's own `master.m3u8` with no session →
  segments generated with **blank** `PlaySessionId` → Emby 400 on every
  segment → playback never starts.
- v0.2.0 proxied only the master playlist server-side — better, but the media
  playlist it pointed at still carried a blank session. Same failure.

## Fix — relay v0.3.0
The relay now mints a fresh `PlaySessionId` (uuid4) per tune request and
resolves the full chain server-side:

1. `GET master.m3u8?PlaySessionId=<S>&...` → variant URL
2. `GET <variant>?PlaySessionId=<S>` → media playlist
3. Rewrite all segment/key/map URIs to absolute URLs
4. Return the media playlist with HTTP 200 (no redirect)

Emby echoes `<S>` into every segment URL, so the player fetches segments
against a valid session.

## IPTV notes (from research)
- Proxy HLS playlists; never 302-redirect session-bound streams.
- Rewrite segment URIs to absolute — some Emby clients 404 on relative ones.
- Don't forget `EXT-X-KEY` / `EXT-X-MAP` URIs when proxying encrypted streams.
- Emby 400s on blank PlaySessionId; Jellyfin tolerates it — test both.
- Emby/Jellyfin ignore `#EXTVLCOPT` and `#KODIPROP` in tuner playlists.
- `tvg-id` wins over `tvg-name` for guide matching; logos must be absolute URLs.

Seth: "Research and fix it like a genius. No more duct tape. Always consult

### What was wrong with v0.4.x
- The relay asked **Emby to seek-transcode** (`master.m3u8?StartTimeTicks=`).
  Emby's variant playlist is gated on its transcode job producing segment 0;
  on seek it hangs **forever** if ffmpeg wedges. Observed directly.
- Double transcode: Emby transcoded to HLS for the relay, then Emby's tuner
  ffmpeg processed the relay's TS output again.
- `schedules.json` (relay) and `epg.json` (guide) drifted — guide showed
  "Jackie Brown" while the relay played a different film.
- 16 zombie ffmpeg processes from the `-stream_loop -1` incident were
  starving the box.

### v1.0 — the relay owns ffmpeg
Per dizquetv / ErsatzTV / Tunarr: **never ask the media server to
seek-transcode.** The relay now:
1. Resolves current program from the timeline.
2. Fetches `GET /emby/Videos/<id>/stream?static=true` (raw bytes, no transcode).
3. Spawns Emby's bundled ffmpeg with a **single input `-ss`** (plain seconds),
   `-c:v copy -c:a copy`, MPEG-TS to stdout pipe.
4. Streams stdout to the tuner as `video/mp2t`. Watchdog kills ffmpeg if no
   bytes in 12s; kills on client disconnect. No HLS, no PlaySessionId, no
   playlist parsing.

Result: first byte in **2–4s** (was 10–15s+, often hanging).

### v1.1 — single-source scheduler
`generate.py` (stdlib only) reads `library.json` (movie pools) and atomically
writes `timeline.json` + `kavitv.xml` + `kavitv.m3u` from one deterministic
timeline (DizqueTV model: `seed(channel, day)`, gapless 24h tiling, 72h
window, UTC). The relay and the guide read the **same** slots — drift is
impossible by construction. `tvg-id` values kept stable (`kavitv.horror`
etc) so Emby's channel identity (and logos) survive.

### v1.2 — robustness
- Dead Emby items pruned from the library (7 of 49 failed static HEAD).
- Offset-0 retry: if ffmpeg fails at the computed seek, retry once from the
  beginning instead of 502.
- Boundary slack (10s) and seek clamping (`[0, duration-10s]`).

### XC bridge — live TV for Flix Pro
The bridge was VOD-only (`get_live_streams` → `[]`). Added `live_tv.py`:
- `get_live_categories` / `get_live_streams` — 3 KaviTV channels (ids
