# VPN on the Fire TV Stick 4K Select (Vega OS) — options ranked by feasibility

**Headline: YES, the stick can ride a VPN — and Seth can build his own client.**
Vega OS gained a system VPN API in the Nov 28–30, 2025 OS update. Six commercial
providers (NordVPN, IPVanish, Surfshark, ExpressVPN, Proton VPN, Le VPN) already
ship native Vega VPN apps using it. The API is in the PUBLIC SDK (0.24.12112).

## The API (verified in SDK source)

`KeplerNetworkManagerInterface` exposes via APMF IDL (OmniKit IPC):

- **`IVpnManager`** — `createVpn`, `getVpnConfig`, `getVpnState`, `addDnsServer`,
  `addRoute` / `deleteRoute`, `addInterfaceAddress`, `setMtu`, `startVpn`,
  `stopVpn`, event listeners
- **`IWireGuardVpnManager`** — `updateWireguardPeer/Interface`,
  `removeWireGuardPeer`, `getWgPeerStats` (last handshake, tx/rx bytes)
- **Privilege required:** `com.amazon.network.privilege.net-vpn-ctrl`
  (declared in manifest `[needs.privilege]`)
- **Config types:** `WgInterfaceConfig` (ip/prefix, pubkey, privkey optional,
  listen port), `WgPeerConfig` (peer pubkey, allowed IPs, endpoint IP/hostname,
  port, keepalive, preshared key)
- **Split tunneling is native:** `addRoute`/`deleteRoute` add/exclude routes —
  exactly KaviVPN's split-tunnel design, expressed in API calls
- **One-time system permission prompt** on first connect (user approves once)

**Caveat:** no prebuilt JS/TurboModule binding ships in the SDK — only C++ IDL.
A custom app needs the `idl-turbo-module` project template to generate JS
bindings (same pattern as any custom native module on Vega).

## Option A — Native KaviVPN client app (BEST, most feasible)

Build `com.kellner.vpn`: a Vega RN app that configures the SYSTEM WireGuard
tunnel to Seth's Oracle Cloud server.

**Build sketch:**
1. `vega project generate --template idl-turbo-module` against the
   `KeplerNetworkManagerInterface` VPN IDL → JS-callable `VpnManager`
2. Manifest: `[[needs.privilege]] id = "com.amazon.network.privilege.net-vpn-ctrl"`
3. UI: big Connect/Disconnect tile, server = Oracle Cloud (fixed, Seth's own),
   status from `getVpnState()` + event listener
4. Config mapping from KaviVPN's `.conf` (generated by `add-client.sh`):
   - `[Interface] Address` → `WgInterfaceConfig.ip`
   - `[Interface] PrivateKey` → `WgInterfaceConfig.privKey`
   - `[Peer] PublicKey` → `WgPeerConfig.pubKey`
   - `[Peer] AllowedIPs` → `WgPeerConfig.allowedIps`
   - `[Peer] Endpoint` → `epIp`/`listenPort` (+ `epType = IP`)
   - `[Peer] PersistentKeepalive` → `keepAlive`
5. Split-tunnel (KaviVPN's torrent-only design): after `createVpn`, call
   `addRoute("10.8.0.0/24")` only (tunnel subnet), NOT `0.0.0.0/0` — everything
   else stays direct. Full-tunnel mode: `addRoute("0.0.0.0/0")`.
6. Kill switch: KaviVPN's socket-binding trick doesn't apply on TV (no per-app
   socket control). Instead: if `VpnState` leaves connected, show a blocking
   full-screen warning; the system tears down routes with the tunnel, so traffic
   fails closed rather than leaking (verify on-device).
7. Distribute via **Live App Testing** (private, full launcher tile). The
   `net-vpn-ctrl` privilege will face Appstore review scrutiny for public
   listing — LAT avoids that entirely.

**Feasibility: HIGH.** API is public, WireGuard is the only protocol the API
supports ("only WireGuard for now" per the IDL docs), and KaviVPN is already
WireGuard. No crypto code to write — the system owns the tunnel.

## Option B — Embedded tsnet (Tailscale) in an app

Proven by `looizao/jellyfin-vega-tailnet` (only public proof, Sep 2026):
Go `tsnet.Server` → cgo C archive → C++ TurboModule → JS. Userspace WireGuard,
no system routes — traffic goes through the app's netstack only.

**Use for:** tailnet access (reach SETHS-PC, Emby, KaviTV relay) — NOT for
general VPN egress. It cannot route other apps' traffic.

**Feasibility: MEDIUM-HIGH** (proven pattern, but app-scoped only).

## Option C — Per-app HTTP/SOCKS proxy

**Not available.** No proxy IDL found in the SDK; no system proxy settings
surfaced for third-party apps. The WebView has no proxy config API. [P]

## Option D — DNS override

Only via the VPN API's `addDnsServer` (tunnel DNS), or at the router level.
No standalone DNS-changer API on Vega. For geo-unblocking SmartDNS-style,
point the router's DHCP DNS at the SmartDNS service — stick-wide, no app needed.

## Option E — Commercial VPN apps (NordVPN, Surfshark, …)

They work today from the Appstore. But they're subscriptions, closed source,
and can't point at Seth's Oracle server. Useful as a *reference* for UX, not
as Seth's solution.

## Option F — VPN at the router

A WireGuard client on the home router (or a second travel router) covers the
stick with zero app work. Downside: all-or-nothing per device (no per-app
split tunnel), and it doesn't travel with the stick.

## The reverse question: subnet routing vs. stick VPN egress

Today the stick is reachable via tailnet because SETHS-PC advertises
`10.0.0.0/24`. If the stick's own default route goes through a VPN tunnel:

- **Inbound still works:** the subnet router delivers packets to 10.0.0.151
  regardless of the stick's outbound path. Kavi's vda/RVG access survives.
- **Stick-initiated tailnet traffic breaks** unless excluded: with a full
  tunnel (`0.0.0.0/0`), the stick's packets to `100.x.x.x` peers would try to
  exit via the VPN server instead of the LAN gateway. **Fix:** split-tunnel —
  `deleteRoute("100.64.0.0/10")` (Tailscale CGNAT range) so tailnet traffic
  stays on the LAN. The Vega API's `deleteRoute` exists precisely for this.
- **KaviVPN's design already anticipates this:** its split-tunnel mode
  (`AllowedIPs = 10.8.0.0/24`) never touches the default route, so the
  tailnet path is unaffected by default. Only full-tunnel mode needs the
  exclusion.

## KaviVPN reuse map

| KaviVPN concept | Vega equivalent |
|---|---|
| `add-client.sh` generated `.conf` | `WgInterfaceConfig` + `WgPeerConfig` structs |
| Split tunnel (`AllowedIPs = 10.8.0.0/24`) | `createVpn` + `addRoute("10.8.0.0/24")` only |
| Full tunnel (`AllowedIPs = 0.0.0.0/0`) | `addRoute("0.0.0.0/0")` |
| Socket-bind kill switch (BiglyBT) | Not portable; use fail-closed routes + blocking UI |
| `server-setup.sh` hardening | Unchanged — server side is identical |
| Port forwarding (`port-forwarding.md`) | Works the same; peer config carries the port |

## Recommendation

**Build Option A** (`com.kellner.vpn`, "KaviVPN" tile): it reuses the entire
KaviVPN server side unchanged, needs only a config-mapping UI + the IDL
TurboModule, and ships privately via LAT. Start with split-tunnel mode
(zero risk to tailnet access), add full-tunnel + `100.64.0.0/10` exclusion
later. Keep Option B (tsnet) for the KaviTV app's control endpoint — the two
complement: system VPN for egress privacy, tsnet for tailnet identity.
